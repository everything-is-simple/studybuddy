## 3. 控件动作覆盖规则

每一项静态控件都至少执行一种真实动作：

- `<a>`：实际 GET 目标并检查 HTTP 状态
- `<button>`：实际点击；浏览器 prompt/confirm 由测试器先注册处理器再点击
- `<input type=text/url/email/date/number>`：实际填写
- `<input type=checkbox/radio>`：实际勾选
- `<input type=file>`：实际选择隔离测试文件
- `<select>`：实际选择可用选项
- `<textarea>`：实际填写
- `role=button` / `role=link`：纳入相同矩阵
- 表单按钮：先填写可填写字段，再执行按钮动作
- 每个控件操作后重新加载页面，避免前一个控件改变 DOM 后影响后续记录

## 6. 中途出现的失败及复核结论

### 6.1 设置页旧测试失败

原测试使用 Node 创建本地 Provider/SMTP 夹具，Python 后端通过本机回环连接不到 Node 监听端口，导致按钮停留在“处理中…”。

复核方式：

- 使用 Python HTTP Provider 夹具重新测试
- 使用 Python SMTP 夹具重新测试
- Provider 成功、失败、恢复全部通过
- SMTP 成功和保存全部通过
- 后端连接测试 30/30 通过

判定：❌ 不是 StudyBuddy 功能缺陷，是原测试夹具环境问题。

### 6.2 任务页错误文案断言不一致

已有页面实际显示的是：

```text
索引服务连接失败，请重试
```

原测试曾期待：

```text
索引服务暂不可用，请重试
```

Python 夹具复测后，失败任务、重试、最终成功链路均通过。页面的实际文案属于安全且稳定的用户文案。

判定：❌ 不是功能链路失败，是旧测试断言与当前文案契约不一致。

### 6.3 任务状态筛选测试顺序依赖

单独运行 `TK-6` 时，没有前置 `TK-5` 生成的成功任务，因此筛选 succeeded 显示空列表。完整任务 describe 顺序中该数据由前置场景产生。

判定：⚠️ 测试之间存在数据依赖，建议后续将 TK-6 自己创建所需状态数据。当前产品页面本身没有发现失败。

### 6.4 逐控件矩阵最初的 4 个失败

最初的 4 项全部是计划页 prompt/confirm 按钮。测试器先等待 click 返回，再处理 dialog，形成死锁。改为点击前注册 dialog handler 后，矩阵结果变为：

```text
549 条记录
479 通过
70 条件阻塞
0 失败
```

判定：❌ 不是产品失败，是测试器自身动作顺序错误。

## 8. 环境限制

- 本机此前存在 IPv4 回环异常，导致部分 Node 本地夹具不可达；本轮用 Python 夹具复测成功。
- 未使用真实外部 AI API Key；AI 生成链路使用 fake provider，真实外部 Provider 仍需实际凭据单独验收。
- SMTP 使用本地 Python SMTP 夹具，没有向真实邮箱发送邮件。
- OCR/ASR 未安装或未配置时，页面按设计显示 `not_configured`/降级状态，不伪造成功。
- 未进行真实多浏览器矩阵；本轮使用 Playwright Chromium。
