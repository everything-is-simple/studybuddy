## 1. 定位与适用范围

`docs/10-开发规范` 的 16 步流程仍是每个任务从登记、计划、TDD 到 Git 收口的基础流程。本文件不废除它，而是在系统集成期增加一层不可省略的“阶段闭环”工作流：当前任务可以持续多个用户主路径阶段，任何阶段完成都必须留下事实、证据、问题和下一闸门，不能把阶段通过写成任务或产品完成。

适用范围：

- T-M5-011 的每一次开发机主路径阶段、断点整改、重跑和重启回读；
- 后续使用机复制、安装包重建和安装后验收阶段；
- 任何会影响系统集成主链、运行资源、真实用户动作、数据生命周期或交付声明的修订。

不适用范围：

- 纯历史任务证据的追补，除非它影响当前问题总账或交付判定；
- 不影响系统集成主链的局部代码维护，仍按 `docs/10` 的常规任务流程执行。

当本文件与下列内容并存时：

1. 用户明确裁决与 `AGENTS.md` 安全边界优先；
2. `01` 定义客观判断模型和证据等级；
3. `02` 是问题、根因、责任和顺序的唯一总账；
4. `03` 是验收和交付顺序的唯一判据；
5. 本文件规定每一阶段如何执行、取证、回填、判定继续或停止；
6. `docs/10` 规定代码任务的 16 步基础纪律，`docs/13` 规定动作/错误/数据/测试/运维追溯内容。

## 2. 阶段对象与不变规则

### 2.1 阶段定义

一个“阶段”是当前系统集成主链中可独立判断的最小连续用户路径，例如：

```text
默认模型配置/发送/重启回读
S2 核心资料导入→转换→normalized_texts→笔记→模块→重启回读
S3-S5 真实课程/模块→练习→错题→重做→冲刺→重启回读
S6/S7/TTS/备份恢复→重启回读
运行资源固化→使用机复制→使用机主路径
安装包安装→空数据主路径
```

阶段不是新的 task-id，不自动创建新的 `.plan/`，也不自动改变当前任务状态。只有用户明确选择新任务，且满足 `AGENTS.md §4.4`，才可建立新任务计划。

### 2.2 永久不变规则

1. 当前阶段只从 `02` 的最高优先级、前置已满足且未关闭的问题开始；不得跳到后续阶段。
2. 每个阶段必须使用 `H:\pi-studybuddy-tmp\runs\<task-id>\<stage-id>\` 下的全新隔离根；不得污染 `%LOCALAPPDATA%\PiStudyBuddy`。
3. 用户可见闭环必须由真实 Electron 的可见 UI 完成。不得以 renderer/CDP 注入、handler/RPC 直调、数据库预置、runtime seed、fixture 或 mock 业务数据替代。
4. 真实外部服务默认不连接。仅在用户明确授权具体服务、凭据与本阶段调用后，才可发送最小脱敏请求；授权不足时，记录受授权阻塞而不是猜测或绕过。
5. 任何失败都先回填 `02`，再按 RED → GREEN → 真实 UI 重跑修复；测试通过不是阶段通过。
6. 每个写入阶段必须包含关闭、重启和可见回读；未完成重启回读最高只能记为 E4。
7. 证据、日志、DOM、报告和 Git 均不得包含完整 UUID、绝对路径、密钥、base URL、请求正文、模型完整输出、学生资料原文或错误栈。
8. `.exe`、安装包和真实生产数据只可在当前阶段范围明确允许时操作；当前 T-M5-011 未获单独授权时，不读取、不暂存、不修改任何 `.exe`。
9. 阶段通过只更新该阶段和对应问题状态；不得把 E4/E5 外推为使用机 E6、安装包 E7、任务 done 或系统可交付。
10. Git 提交、推送、合并与任务收尾仍须用户单独明确授权；阶段结束默认停在“证据已登记，等待下一指令”。

## 3. 固定工作流

每一阶段都按以下 12 步执行。步骤可在同一会话连续进行，但不得跳过或把未执行项标为完成。

### 步骤 1：恢复上下文与确认当前阶段

- 阅读 `AGENTS.md`、00 索引、04-Todo、当前唯一 `.plan/`、系统集成 01-04，以及与阶段有关的 01-09/13 文档。
- 核验 `git status`、当前分支、运行根和未跟踪文件；不读取被排除的安装包。
- 从 `02` 选定一个问题或一组不可拆分的连续主链动作，写明本阶段 ID、目标、前置、非目标和停止条件。

**退出条件**：当前阶段、证据等级目标、用户授权边界和禁止项明确。

### 步骤 2：建立隔离运行根与证据清单

- 创建全新的 `<stage-id>` 子目录和隔离数据根。
- 记录启动前空态、运行时版本、数据根标识、是否允许外部调用、是否允许真实凭据。
- 预先列出用户动作、预期 UI 状态、预期数据事实、重启回读项、问题 ID、应产出的脱敏证据。

**退出条件**：运行根为空，证据清单能区分 UI、数据、错误和重启结果。

### 步骤 3：生产链盘点与 RED 断言

- 阅读生产入口、renderer、preload、contract、handler、数据/运行资源链，以及受影响的既有测试。
- 明确每个用户动作对应的 UI、RPC、领域逻辑、数据资产和错误恢复；必要时引用 `ACT-*`、`ERR-*`、`DATA-*` 资产。
- 若已知或实际发现断点，先写最小失败测试或可复现观察，保存 RED 证据；不得先写实现再补测试。

**退出条件**：断点的责任层和预期行为可验证；若无断点，记录“无代码整改需要”的依据。

### 步骤 4：最小整改与自动化回归

- 只修改使当前断点通过的最小生产代码、测试和必要权威文档。
- 运行定向 unit/integration/Electron E2E、type-check 和 build；外部服务仍使用受控 mock，除非已授权真实调用。
- 失败时回到步骤 3，追加问题或修复记录；不得用跳过或 fixture 掩盖。

**退出条件**：自动化能证明当前断点的回归边界，且没有把自动化当作 UAT 成功。

### 步骤 5：真实 Electron 可见 UI 主路径

- 以真实生产入口启动 Electron，在全新隔离根执行全部用户动作。
- 不经注入、直调或数据库预置制造前置；前置若不可由 UI 创建，视为产品断点并停止向后宣称闭环。
- 记录每一步成功、失败、禁用、重试和用户可见反馈；只保存脱敏 DOM、截图或结构化状态。

**退出条件**：阶段动作成功到达预期可见状态，或记录了首个真实断点。

### 步骤 6：数据事实与后续消费核对

- 核对 SQLite/受控文件/配置的真实持久化事实、完整性和后续业务消费结果。
- 数据核对只用于验证 UI 操作结果，不能用来替代 UI 操作或创建业务前置。
- 对写入阶段执行 `PRAGMA integrity_check` 或等价受控检查，并记录脱敏摘要。

**退出条件**：UI 成功、数据事实与下一业务消费一致；不一致即回到步骤 3。

### 步骤 7：关闭、重启与可见回读

- 正常关闭应用，再以同一隔离根启动真实 Electron。
- 从可见 UI 回读本阶段写入的关键数据、状态和可继续动作。
- 重启失败、数据丢失、错误不可恢复或仅能通过直调读取，均视为阶段失败。

**退出条件**：写入阶段达到 E5；纯无持久化观察阶段可明确记录其最高 E4/E3。

### 步骤 8：阶段判定

只能选择以下之一：

| 判定 | 条件 | 后续动作 |
|---|---|---|
| `passed` | 主路径、数据事实、重启回读和隐私边界均通过 | 更新 01/02/03/当前计划，等待用户选择下一阶段 |
| `failed` | 出现产品、数据、运行资源或隐私断点 | 先登记问题，回到步骤 3 做 RED→GREEN |
| `blocked` | 缺少用户授权、凭据、合法依赖、外部资源或前置 UI | 登记阻塞、所需授权/资源和不可替代原因；停止 |
| `partial` | 只完成可独立证明的子路径，但下一动作未满足 | 记录证据等级和未覆盖项；不得推进或宣称完整通过 |

### 步骤 9：问题、进度与证据回填

每次阶段结束必须同步：

- `02`：问题状态、根因、责任边界、证据等级、运行根、未解决项；
- `01`：客观进度及不得外推的边界；
- `03`：当前验收位置、下一闸门和不得跳过的项；
- `.plan/00-当前任务.md`：当前阶段结果、任务仍在执行或阻塞的事实；
- `04-Todo`：仅在任务登记、状态、统计或证据事实需要更新时同步，不得把阶段证据误写成任务 done；
- `docs/13` 追溯资产：只有动作/错误/数据/运维目录实际受影响时更新。

每次回填都必须写明“通过的范围”和“仍未通过的范围”。

### 步骤 10：阶段质量门

按实际改动与范围运行：

- Node 24 基线的 type-check、定向测试、受影响真实 Electron E2E；
- build 或等价本地已安装工具链构建；若包管理网络故障，记录环境事实，不得伪称未执行的命令通过；
- `node scripts/check-docs-governance.mjs`；
- `git diff --check`；
- 对涉及安全/契约的改动运行相应检查。

**退出条件**：实际命令、结果、未运行原因和环境失败均有证据；不得用历史全绿替代本阶段验证。

### 步骤 11：独立审查与范围核验

- 以独立审查视角核对阶段问题、代码/文档变更、证据等级、数据事实、隐私、未解决项和禁止项。
- 对重大设计/治理基线变更按 `AGENTS.md §11.4` 完成至少两名独立审查者交叉核对。
- 发现 P0/P1 或事实夸大，回到步骤 3/9 修正。

**退出条件**：无未处置的阻塞性问题；未完成独立审查时如实标记，不报告阶段正式通过。

### 步骤 12：停下、等待下一授权

- 默认不创建新任务计划、不改变当前任务为 done、不提交/推送/合并。
- 向用户报告已验证事实、证据等级、运行根、问题状态、质量门、工作区状态和下一闸门。
- 只有用户明确批准后，才开始下一阶段、创建新任务或执行 Git 操作。

## 4. 与 16 步开发流程的映射

| 系统集成阶段动作 | `docs/10` 基础流程对应 | 说明 |
|---|---|---|
| 步骤 1-2 | 1-2 | 保留文档入口、单一任务和边界门禁 |
| 步骤 3-4 | 6-10 | 对真实断点执行 RED→GREEN、实现和定向自动化 |
| 步骤 5-7 | 11 + 13 的真实 UAT/数据生命周期要求 | 系统集成不可省略的可见 UI、数据事实、重启回读循环 |
| 步骤 8-9 | 12-13 | 阶段判定、问题总账和事实同步，不等同任务收尾 |
| 步骤 10-11 | 8-15 | 按影响范围质量门、治理检查、独立审查 |
| 步骤 12 | 16 的授权边界 | 默认停止；Git 或任务收尾必须另获授权 |

系统集成阶段若产生一个新的独立任务，仍必须先满足 `docs/10` 的步骤 1-5 和 `AGENTS.md §4.4`，不得以本工作流规避计划批准门禁。

## 5. 阶段证据最小模板

每个阶段在运行根保存一个脱敏报告，至少含：

```markdown
# <stage-id> 阶段报告

- 当前任务：
- 问题 ID：
- 目标与非目标：
- 隔离运行根：
- 外部服务/凭据授权：未使用 / 已授权且最小调用 / blocked
- 用户动作与实际结果：
- 数据事实与完整性摘要：
- 重启回读：通过 / 失败 / 不适用（说明原因）
- 证据等级：E0-E7
- RED→GREEN：不适用 / 失败断言 / 修复与重跑
- 隐私检查：UUID、路径、密钥、正文、栈
- 问题总账回填：
- 已运行质量门及结果：
- 阶段判定：passed / failed / blocked / partial
- 未解决项与下一闸门：
- Git 状态：
```

## 6. 终止条件与 E7 完成判据

本固定工作流持续执行，直至 `03` 的整体交付判据全部满足，并取得安装包安装后空数据主路径的 E7 证据。达成 E7 前：

- 不得将历史 task done、阶段 E5 或使用机 E6 替代安装包 E7；
- 不得删除 `02` 中仍未关闭的问题；
- 不得以新的平行流程、一次性 prompt 或未经登记的测试后门替代本文件；
- 每次新增断点都必须回到本工作流步骤 3 或步骤 8。
