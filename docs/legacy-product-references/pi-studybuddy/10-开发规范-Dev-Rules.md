## T-M5-011 当前开发口径

先在当前开发机按真实用户路径把系统跑通；每修复一条主路径就在开发机复跑并记录结果；开发机闭环后，复制同一套运行资源、默认配置和启动拓扑到使用机。单件、集成和自动化测试用于定位问题，不替代主路径运行。

`docs/10` 的 16 步仍约束任务级实施和 Git 收口；系统集成任务的每一个主路径阶段还必须按 [系统集成/04-系统集成固定工作流与阶段门禁](./系统集成/04-系统集成固定工作流与阶段门禁.md) 执行 12 步阶段循环。阶段通过不等于任务 done；该第四份系统集成文件已按用户裁决立即执行，治理基线审查仍待 `AGENTS.md §11.4`。

## 1. 概述

### 1.1 文档定位

本文件是 pi-studybuddy 每个**开发任务**的标准化执行流程。它不重复设计文档的内容，而是规定"从 04-Todo 登记的任务行 → 到 origin/master 推送完成"之间的 16 个必经步骤。

### 1.2 与其他文档的关系

```
AGENTS.md §4-§8（任务铁律 + TDD + 拆分组合 + 受控收尾 + Git 纪律）
    ↓ 细化为操作步骤
docs/10-开发规范（本文件，16 步流程）
    ↓ 指导执行
docs/04-Todo（任务注册表）+ .plan/（行动计划）+ .record/（实施记录）
    ↓ 产出
src/（代码）+ tests/（测试）+ docs/（文档同步）
```

### 1.3 流程铁律

1. **16 步顺序不可跳越**：每步完成后才能进入下一步；任一步骤失败退回上一步
2. **状态实时同步**：任务状态变更同步到 04-Todo，不只存在于聊天
3. **证据留痕**：每步产出可审计的证据（计划/测试日志/提交哈希/实施记录）
4. **用户授权节点**：§3 第 5 步（计划批准）和第 16 步（提交交付）必须用户明确授权
5. **提示词资产不替代计划**：`.pi/prompts/task-execution/` 只提供标准化入口、过程和验收主题；任务仍必须经过 04-Todo 登记、单一 `.plan/`、用户批准、测试与 Git 授权。

## 3. 16 步详解

### 步骤 1：读文档、定边界

**目标**：建立完整上下文，明确任务范围

**操作**：
1. 按 AGENTS.md §0 强制入口顺序读取：AGENTS.md → 00-索引 → 04-Todo → .plan/00-当前任务.md → 相关设计文档
2. 在 04-Todo 找到或新建任务行（task-id / 标题 / 分类 / 子系统 / 优先级 / 状态 / 治理阶段 / 关联文档 / 产物 / 证据 / 备注）
3. 明确任务边界：做什么、不做什么、依据哪份设计文档的哪个章节

**产出**：任务行已登记在 04-Todo，范围明确
**失败处理**：设计文档缺失或冲突 → 停止，修复治理文档或请求用户裁决

### 步骤 2：检查文档门禁

**目标**：确认前置条件满足，可以开工

**操作**：
1. 确认 AGENTS.md §4.4 单一执行任务门禁三项前置：
   - 上一项任务已完成并在 04-Todo 记录
   - 用户已明确选择该任务并批准开工
   - 该任务即将进入实施
2. 确认 `.plan/` 无其他执行中任务
3. 确认 master 分支干净（`git status` 无 unstaged 改动）

**产出**：门禁通过，可以创建计划
**失败处理**：门禁未通过 → 等待前置任务完成或请求用户裁决

### 步骤 3：编写 .plan/ 计划

**目标**：为任务创建唯一行动计划

**操作**：
1. 创建 `.plan/T-<里程碑>-<序号>-<scope>.md`（如 `T-M0-001-electron-skeleton.md`）
2. 计划文件必含以下章节（参考 .pi/prompts/plan.md 模板，待创建）：
   - 任务目标（做什么、为什么、依据哪份设计文档）
   - 范围与非目标（明确不做什么）
   - 文件清单（将创建/修改的文件路径）
   - 接口设计（RPC 方法 / registerTool 工具 / 数据表）
   - 测试策略（单件/集成/冒烟/E2E 各断言什么）
   - 五阶段治理定位（当前任务处于哪个组件的哪个阶段）
   - 依赖关系（前置任务、组件依赖）
   - 预期产物（代码/测试/文档更新）
3. 创建 `.plan/00-当前任务.md` 指向该计划

**产出**：`.plan/T-XX-NNN-*.md` 计划文件 + `.plan/00-当前任务.md` 指针
**失败处理**：计划不完整 → 补充后重审

### 步骤 4：独立审查计划

**目标**：确保计划可执行、无遗漏

**操作**：
1. 以审查者视角通读计划，检查：
   - 是否覆盖任务目标全部要求
   - 文件清单是否完整
   - 接口设计是否与 06-API 契约一致
   - 测试策略是否覆盖关键不变量
   - 是否违反任何铁律（AGENTS.md §4-§9）
2. 记录审查意见（可直接在计划文件底部追加"审查记录"章节）

**产出**：审查记录（意见/通过/需修订）
**失败处理**：审查未通过 → 修订计划后重审

### 步骤 5：用户批准计划（★ 用户授权节点）

**目标**：获得用户明确批准，方可开工

**操作**：
1. 向用户汇报计划摘要：目标 / 范围 / 文件清单 / 测试策略 / 预期产物
2. 请求用户明确批准（"批准" / "开工" / "继续"）
3. 批准后在计划文件底部记录："用户已于 YYYY-MM-DD HH:MM 批准开工"

**产出**：用户批准记录
**失败处理**：用户未批准或有修改意见 → 修订计划后重新请求批准
**禁止**：未经用户批准直接写业务代码

### 步骤 6：拆分任务、逐项实现

**目标**：按计划拆分实现，每项独立可验证

**操作**：
1. 在任务分支上工作：`git checkout -b <executor>/<work-id>-<scope>`（AGENTS.md §8.1）
2. 按计划文件清单逐项实现，每项完成后：
   - 运行该项的单件测试
   - 确认该项无 regression
3. 遵循 pi AGENTS.md 代码质量纪律：
   - 改前先完整读文件
   - 禁 `any`、禁内联 `import()`
   - 只用可擦除 TS 语法
   - 不改生成产物（改生成脚本）

**产出**：任务分支上的代码实现
**失败处理**：实现困难 → 退回计划修订；测试失败 → 修复后继续

### 步骤 7：编写或更新测试

**目标**：TDD——测试先于或同步于实现

**操作**：
1. 遵循 TDD 纪律（AGENTS.md §5）：RED → GREEN → REFACTOR
2. 测试分层（08-Test §2）：
   - **单件测试**（阶段 2）：vitest（TS）+ pytest（Python 桥）
   - **集成测试**（阶段 3）：extension×pi 底座契约 + 钩子协作
   - **系统冒烟**（阶段 5a）：真实 Electron + 真实组件（外部 mock）
   - **系统 E2E**（阶段 5b）：Playwright 全链回归
3. 测试运行数据隔离：`H:\pi-studybuddy-tmp\runs\<task-id>\`
4. 不连真实外部服务（AI/SMTP/飞书/whisper.cpp/WPS COM 全 mock）

**产出**：测试文件 + 测试通过证据
**失败处理**：测试失败 → 修复实现 → 重跑

### 步骤 8：type-check

**目标**：类型安全零错误

**操作**：
1. `pnpm type-check`（M0 启动后补全命令）
2. 零错误、零警告
3. TS strict 模式全开

**产出**：type-check 通过日志
**失败处理**：有错误 → 修复 → 重跑

### 步骤 9：build

**目标**：构建成功

**操作**：
1. `pnpm build`
2. 无构建错误
3. 产物体积合理（无意外膨胀）

**产出**：构建产物 + 成功日志
**失败处理**：构建失败 → 修复 → 重跑

### 步骤 10：test

**目标**：全部测试通过

**操作**：
1. `pnpm test`（vitest 全量）
2. `python -m pytest`（Python 桥测试，如涉及）
3. 确认无 skip（除非有明确原因并记录）

**产出**：测试通过日志
**失败处理**：有失败 → 修复 → 重跑

### 步骤 11：smoke / E2E

**目标**：端到端可走通 + 铁律不破

**操作**：
1. 系统冒烟（08-Test §5）：
   - S1-S7 主路径冒烟（如涉及）
   - TTS 跨子系统冒烟（如涉及）
   - 备份恢复冒烟（如涉及）
   - 家长报告脱敏冒烟（如涉及）
   - workspace-path-guard 冒烟（如涉及）
   - credential-vault 冒烟（如涉及）
2. 安全不变量校验脚本：`scripts/check-desktop-security.mjs` 六条断言全过（08-Test §5.7）
3. 受影响 E2E（08-Test §6）：
   - 按任务范围运行相关 E2E 用例
4. 运行统一质量门：`pnpm verify`（scripts/verify.mjs，待创建）

**产出**：冒烟/E2E 通过日志 + 安全不变量六条全过
**失败处理**：失败 → 退回上一阶段修复 → 记录修复证据（04-Todo §8 修复记录区）

### 步骤 12：独立代码或文档审查并修复

**目标**：独立视角发现问题

**操作**：
1. 以审查者视角通读本次全部改动：
   - 代码是否符合设计文档
   - 是否违反任何铁律
   - 是否有过度工程化
   - 注释/文档是否同步更新
2. 发现问题立即修复
3. 修复后重跑 type-check + test（步骤 8-10）

**产出**：审查通过 + 修复记录
**失败处理**：发现重大问题 → 退回步骤 6 重新实现

### 步骤 13：更新任务清单和文档

**目标**：状态同步到 SoT

**操作**：
1. 更新 04-Todo：
   - 任务状态改为 `done`（或 `testing` → `done`）
   - 登记 evidence（测试通过证据、提交哈希）
   - 如有修复记录，写入 04-Todo §8 修复记录区
2. 如 API 合同变化，更新 06-API 契约
3. 如数据模型变化，更新 05-ERD
4. 如工作流变化，更新 07-Workflow
5. 如涉及对话 Tab 等已审查批准文档的实质变更，走显式变更评审

**产出**：04-Todo + 相关设计文档已同步
**失败处理**：文档与代码不一致 → 补齐后继续

### 步骤 14：文档治理检查

**目标**：文档治理自动化门禁

**操作**：
1. 运行 `scripts/check-docs-governance.mjs`（待创建）：
   - 文件名匹配 `^\d{2}-.+-[A-Za-z0-9-]+\.md$`
   - 每份文档在 00-索引中登记
   - 旧草稿名不得重新出现
   - 版本号一致性
2. 零错误通过

**产出**：文档治理检查通过日志
**失败处理**：有错误 → 修复 → 重跑

### 步骤 15：diff 检查

**目标**：提交前最终核查

**操作**：
1. `git diff --check`（无空白错误）
2. 人工核查 diff：
   - 无意外文件提交（密钥/.env/node_modules/资料原文/完整 UUID）
   - 无 debug 残留（console.log / 调试代码）
   - 无大段注释掉的代码
3. 确认只提交本 session 改的文件

**产出**：diff 检查通过
**失败处理**：有问题 → 修复 → 重新检查

### 步骤 16：提交交付（★ 用户授权节点）

**目标**：用户授权后提交并推送

**操作**：
1. **必须用户明确要求**才能执行提交/推送/合并（AGENTS.md §7 禁止自动提交）
2. 提交纪律（AGENTS.md §8.3）：
   - `git add <显式路径>`（禁 `git add -A` / `git add .`）
   - commit message：`type(scope): 中文描述`
3. 合并到 master（AGENTS.md §8.2）：
   - `git checkout master`
   - `git pull --ff-only`
   - `git merge --ff-only <task-branch>`
4. master 复验：在 master 上重跑 type-check + test + smoke
5. 推送 origin/master
6. 更新 04-Todo：登记提交哈希 + 推送状态
7. 创建实施记录 `.record/T-<里程碑>-<序号>-实施记录.md`（8 章节，AGENTS.md §7.1）

**产出**：origin/master 推送成功 + 04-Todo 证据齐全 + .record 实施记录已创建
**完成判据**（AGENTS.md §8.4 三者齐全）：
1. docs/04-Todo 证据已登记
2. master 分支复验通过
3. origin/master 推送成功

**失败处理**：推送失败 → 排查原因（如远程有新提交 → `git pull --rebase` 后重推）；冲突 → 停下不强推

## 4. 中断恢复

开发会话中断后恢复时：

```
1. 读 .plan/00-当前任务.md → 确认当前任务
2. 读 .plan/T-XX-NNN-*.md → 确认进度（哪些步骤已完成）
3. git status → 检查半成品（不留无说明的 unstaged 代码）
4. 从第一个未完成步骤继续
```

**禁止**：中断后凭聊天记忆继续施工——必须重读文档建立上下文。

## 5. 任务状态机与 16 步映射

```
pending ──→ in_progress ──→ testing ──→ done
  步骤1-5      步骤6-11       步骤12-15     步骤16
  (准备)       (执行)         (收尾)        (交付)
```

| 状态 | 对应步骤 | 进入条件 | 退出条件 |
|---|---|---|---|
| `pending` | — | 任务登记后默认 | 步骤 5 用户批准 |
| `in_progress` | 6-11 | 用户批准 | 步骤 11 smoke 通过 |
| `testing` | 12-15 | smoke 通过 | 步骤 15 diff 检查通过 |
| `done` | 16 | diff 检查通过 + 用户授权提交 | origin/master 推送成功 |
| `blocked` | 任意 | 依赖未就绪 / 测试失败 | 修复后回 `in_progress` |
