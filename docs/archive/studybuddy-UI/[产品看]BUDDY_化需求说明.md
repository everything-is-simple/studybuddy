## 为什么要做 Buddy 化？

### 当前痛点：作者都不想用自己的产品

**现状**：
- 投入两个月开发，功能完整，637 个后端测试通过，551 个浏览器测试通过
- 21 个页面全部审核通过，链接清晰，处理逻辑清晰
- 但作者自己打开 Chrome 页面时，感觉"好怪异"，"一点都不能担当 Buddy"

**根本原因**：
> 界面是按"能被脚本点中、能被截图、能写入 P3 证据"设计的，不是按"一个人愿意多留十秒"设计的。

前端的第一用户 = 测试脚本（Playwright）和两台审核 Agent，不是真实人类（家长、孩子）。

### 七大核心问题

| 问题 | 现状 | 用户感受 |
|---|---|---|
| 1. 界面语气 | 演示稿风格："今日任务""你的学习日程" | 像在看产品说明书 |
| 2. 概念模型 | 8+ 项目管理概念（目标/模块/依赖/节奏） | 像在用 Jira |
| 3. Loading 状态 | 三个串行 loading | 像在等数据库查询 |
| 4. 状态标签 | 46 种状态标签 | 不知道"来源待复核"是什么 |
| 5. 页面跳转 | Today 需要进入 plan-detail 才能开始学习 | 像在爬楼梯 |
| 6. 错误提示 | 开发者语言：`study_plan_dependency_cycle` | 看不懂 |
| 7. 测试绑架 | 所有按钮都有 `title="[1] 导入文件夹..."` | 像在看测试报告 |

## 要达到什么效果？

### 核心目标：用户愿意每天打开

**好的产品 = 用户愿意每天打开**  
**通过测试的产品 ≠ 好的产品**

### 成功标准：三个"一"

1. **一句话就懂**：打开页面，一句话就知道要干什么
   - ❌ 错误："今日任务""你的学习日程""查看今日分配的学习任务和进度"
   - ✓ 正确："今天学什么？"

2. **一键就开始**：核心流程 ≤ 3 步
   - ❌ 错误：today → plan-detail → 点"开始学习" → 填表 → 确认（5 步）
   - ✓ 正确：Today → 点“开始学习” → 点“记录完成”，核心操作不离开 Today

3. **一眼就看到反馈**：有鼓励、有成就感
   - ❌ 错误：状态变成"已完成"，没有任何反馈
   - ✓ 正确："今天真棒！已经学了 30 分钟"

---

## 需求边界：不做什么

### 明确不做的事（避免范围蔓延）

1. **不推倒重来**
   - 现有 21 个页面保留，作为"高级功能"
   - 637 个后端测试、551 个浏览器测试全部保留
   - 测试辅助属性（`data-od-id`、`aria-label`）保留

2. **不重做 CSS**
   - 不改颜色系统（灰白色保留）
   - 不改组件库（继续用现有 `app.css`）
   - 只调整文案、交互流程、页面结构

3. **不做复杂动画**
   - 不做 3D 动画、粒子效果
   - 只做简单的进度条、完成反馈
   - 优先功能可用，再考虑视觉效果

4. **不做移动端适配**（暂时）
   - 短期只做桌面端（Chrome/Edge）
   - 移动端适配列入长期规划

## 需求分层：三种用户，三个视图

### 为什么要分层？

**问题**：现在所有页面都是"管理后台"风格，要求所有用户都懂项目管理。

**方案**：按用户需求分三层，每层只暴露必要功能。

### 层级 1：学生视图（核心需求）

**目标用户**：小学生（五年级）

**核心需求**：
1. **知道今天学什么**：一打开就看到今天的学习内容
2. **一键开始学习**：不需要理解"目标/模块/计划"
3. **看到学习进度**：知道学了多少、还有多少
4. **获得鼓励反馈**：完成后有成就感

**不需要的功能**：
- 不需要"创建计划""配置节奏""管理依赖"
- 不需要看到"来源链接""切片候选""Provider 配置"

**成功标准**：
- 孩子打开页面，3 秒内知道要干什么
- 点一个按钮就能开始学习
- 学完后会说"我今天学了 X 分钟"

### 层级 2：家长视图（简化版）

**目标用户**：家长

**核心需求**：
1. **快速安排学习**：3 步建计划（上传教材 → 选择时间 → 开始）
2. **查看学习报告**：本周学了几天、完成率、错题数
3. **调整设置**：学习时间、提醒、高级设置

**不需要的功能**：
- 不需要手动"建目标""建模块""配依赖"
- 不需要理解"来源链接""切片索引""向量检索"

**成功标准**：
- 家长 5 分钟内完成一个学习计划的创建
- 一眼看懂孩子本周学习情况
- 需要精细控制时，能进入"高级设置"

### 层级 3：后台/高级功能（现有页面）

**目标用户**：需要精细控制的高级用户、开发者

**核心需求**：
1. **完整的项目管理能力**：手动建目标、建模块、配依赖、调节奏
2. **精确的数据控制**：来源链接、切片管理、Provider 配置
3. **系统管理**：数据库、日志、备份、迁移

**保留功能**：
- 现有 21 个页面全部保留
- 所有测试辅助属性保留
- 所有 46 种状态标签保留在后台

**成功标准**：
- 所有现有功能正常工作
- 所有测试继续通过
- 只在"高级设置"入口可见

## 需求优先级：分三期推进

### 第一期：短期速效（1 天内，P0）

**目标**：快速改善核心体验，让作者自己愿意用

**核心需求**：
1. **today.html 改造**
   - 去掉演示稿语气
   - 合并 loading 状态
   - 添加"一键继续"大按钮
   - 任务卡片改为可展开（不跳转）

2. **错误提示改造**
   - 所有错误提示加"怎么办"
   - 错误码改成人话

3. **状态简化**
   - 前端只显示 3 种状态（可用/处理中/有问题）

**成功标准**：
- 作者打开 today.html 时不再感觉"怪异"
- 点击"开始学习"不再需要跳转两次页面
- 看到错误时知道怎么解决

**工作量估算**：
- today.html 改造：4 小时
- 错误提示改造：2 小时
- 状态简化：2 小时
- 测试验证：2 小时
- **总计：10 小时（1 天）**

### 第二期：中期改造（1 周内，P1）

**目标**：建立三层架构，分离用户群体

**核心需求**：
1. **创建学生视图**
   - 新建 `student.html`（极简界面）
   - 只显示今天的学习内容和一键开始按钮

2. **简化家长视图**
   - 新建 `parent.html`（3 步建计划）
   - 学习报告、设置入口

3. **添加进度可视化**
   - 进度条、连续天数、完成动画

**成功标准**：
- 学生打开 `student.html` 时，3 秒内知道要干什么
- 家长 5 分钟内完成一个学习计划
- 完成任务后有鼓励反馈

**工作量估算**：
- 学生视图：8 小时
- 家长视图：12 小时
- 进度可视化：4 小时
- 测试验证：4 小时
- **总计：28 小时（1 周）**

### 第三期：长期重构（按需，P2）

**目标**：做成真正的产品

**核心需求**：
1. **架构改 SPA**（React/Vue）
2. **加 AI 对话入口**（右下角悬浮球）
3. **加家长/学生双视图切换**
4. **移动端适配**（响应式设计 + PWA）

**成功标准**：
- 页面切换不刷新
- 可以语音问"今天学什么"
- 手机上也能正常使用

**工作量估算**：
- SPA 改造：40 小时
- AI 对话入口：16 小时
- 双视图切换：8 小时
- 移动端适配：24 小时
- **总计：88 小时（2-3 周）**

## 需求验收标准

### 定性标准：用户体验

1. **作者愿意每天打开**
   - 作者自己使用 StudyBuddy 辅导孩子学习
   - 孩子愿意每天打开学生视图

2. **5 秒懂、3 步做**
   - 打开页面 5 秒内知道要干什么
   - 核心流程 ≤ 3 步完成

3. **有鼓励、有成就感**
   - 完成任务后有反馈
   - 连续学习有鼓励

### 定量标准：技术指标

1. **性能不退化**
   - 页面加载时间 ≤ 2 秒
   - 交互响应时间 ≤ 500ms

2. **测试全部通过**
   - 637 个后端测试通过
   - 551 个浏览器测试通过
   - 新增页面补充测试覆盖

3. **代码质量不下降**
   - 源码体积增长 < 20%
   - 不引入新的技术债

## 需求风险与应对

### 风险 1：范围蔓延

**风险描述**：改着改着就想推倒重来，做成 SPA、改 CSS、做复杂动画

**应对措施**：
- 严格按三期推进，第一期只做 P0
- 每期结束后验收，确认效果再进入下一期
- 不做的事清单写在需求文档里，随时提醒自己

### 风险 2：测试失败

**风险描述**：改完后原有测试挂了，要花大量时间修测试

**应对措施**：
- 测试辅助属性全部保留（`data-od-id`、`aria-label`）
- 改动前先跑一遍测试，确认基线
- 改动后立即跑测试，发现问题立即修复

### 风险 3：用户不买账

**风险描述**：改完后作者还是不想用，孩子也不愿意用

**应对措施**：
- 每期改完后让作者试用，收集反馈
- 保留现有 21 个页面作为"后路"
- 可以随时回退到原有版本

### 核心需求（一句话）

> 让 StudyBuddy 从"测试脚本看的管理后台"变成"用户愿意每天打开的学习伙伴"

### 三个关键指标

1. **作者愿意用**：作者自己使用 StudyBuddy 辅导孩子学习
2. **5 秒懂、3 步做**：核心流程简化到 3 步以内
3. **有鼓励、有成就感**：完成任务后有反馈

### 三期推进

1. **第一期（1 天）**：today.html 改造 + 错误提示 + 状态简化
2. **第二期（1 周）**：学生视图 + 家长视图 + 进度可视化
3. **第三期（按需）**：SPA 改造 + AI 对话 + 移动端适配

### 记住

**好的产品 = 用户愿意每天打开**  
**通过测试的产品 ≠ 好的产品**
