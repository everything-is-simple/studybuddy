# StudyBuddy Buddy 功能实施 Workflow

> 版本：v1.0
> 创建日期：2026-09-28
> 适用范围：StudyBuddy Buddy 化设计、需求及任务分解文档中的单项功能任务（例如 P0-01、P0-02、P1-01）。
> 权威约束：`H:\studybuddy\AGENTS.md`、`docs\[所有角色看]AI_AGENT_TASK_DIALOGUE_TEMPLATES.md`、对应 Buddy 产品设计/需求/任务文档。

## 1. Workflow 目标

把一项用户可感知的 Buddy 需求，从文档要求转换成有边界的代码改动、与之同步的测试和可核验证据。每次只实施一个可判定任务；不以“顺便做得更完整”为由扩大范围。

本流程不替代项目执行协议。所有任务仍按以下阶段顺序推进：

```text
P0 任务边界确认 → P1 真实状态读取 → P2 真实操作执行 → P3 证据核对 → P4 交付与结论
```

状态统一使用 `PASS`、`FAIL`、`BLOCKED`、`LIMITED`、`NOT_APPLICABLE`、`NOT_VERIFIED`。代码已修改或测试通过，不自动等于真实用户路径 `real-pass`。

## 2. 单项任务启动卡

开始前填写下列字段；未明确的信息不得视为授权。

```text
任务编号：<例如 P0-01>
执行角色：StudyBuddy 实施与验证 Agent
唯一目标：<一个可判定的用户可感知结果>
当前阶段：P0
需求来源：<绝对路径 + 章节/任务编号>
必须读取：<设计、需求、任务拆解、Agent 模板、目标代码、相关测试>
允许读取：<绝对路径清单>
允许写入：<绝对路径清单；包含需要同步的测试>
指定工具/命令/URL/数据根：<原样列明；没有就写无>
禁止操作：<例如不改 API、不触碰正式数据、不调用真实 Provider>
成功判定：<可观察、可重复检查的条件>
证据位置：<按 Prompt 指定；未指定时只报告实际终端结果，不自行扩大落盘范围>
停止条件：<路径、授权、行为、工具或证据条件不满足时停止并 BLOCKED>
```

若任务要求可视浏览器操作，却未指定/授权浏览器、服务、URL、端口、数据根及页面副作用，不得自行启动正式服务或改用别的方式冒充真实浏览器验收。先按项目规则返回 `BLOCKED` 或等待补充授权。

## 3. 执行步骤

### P0：锁定目标和边界

1. 读取任务涉及的 Buddy 设计指南、需求说明、任务拆解和 AI Agent 执行模板；若任务属于特定阶段，还要读取该阶段的权威约束。
2. 把任务描述拆成：目标、允许改动、明确不做、验收条件、测试范围、停止条件。
3. 区分任务拆解里的“示例”与真实实现要求。代码片段、文件行号、API 名称、预估工时只是线索，除非已核对当前源码，不可直接照搬。
4. P0 只确认边界，不代表代码或产品功能已通过。

### P1：读取当前真实状态

1. 检查仓库工作区与基线提交，保留既有用户改动；不得清理或覆盖无关变更。
2. 读取目标页面、引用的共享脚本/样式，以及所有可能依赖目标行为的测试。
3. 搜索目标旧文案、选择器、路由或行为断言，建立“实现位置 ↔ 测试位置”清单。
4. 对照现状检查任务文档：确认目标描述仍适用于现有实现，标出过期示例或事实差异。
5. 仅完成读取和计划；未取得 P2 写入授权时不得修改。

### P2：实施最小可用改动

1. 仅修改启动卡明确授权的文件；优先复用项目现有技术栈、组件、命名、API 和状态管理。
2. 先实现任务的最小用户可感知结果，不顺手重构页面、共享架构或相邻 P0/P1 项。
3. 修改用户可见文案时，保留稳定的测试辅助属性；同步更新那些确实断言旧用户可见行为的测试契约。
4. 不为了让测试通过而削弱断言、用固定等待掩盖竞态，或把 API/静态检查当成用户路径证据。
5. 不新增真实 Provider、OCR、ASR、邮件、飞书、正式数据或秘密相关副作用，除非任务逐项明确授权。
6. 不因测试工具需要而增加面向用户的冗长标签、测试编号或调试信息。

### P3：分层验证与证据核对

按风险从窄到宽执行，并报告精确命令和实际结果：

1. **差异检查**：检查 diff 只涉及授权文件；执行 `git diff --check`。
2. **静态/定向检查**：确认旧实现已按范围修改、必要测试断言已同步；运行目标相关的静态检查或 focused test。
3. **浏览器回归**：运行目标页面和直接依赖的 Playwright 用例。遵守测试类别：A 类用户路径不能通过业务 API 预置数据或获取关键 ID；B 类故障注入需标注为非纯用户路径。
4. **扩大验证**：仅当共享 API、存储、迁移、基础设施或跨模块行为受影响时扩大到相应回归；改动页面交互时按项目要求运行浏览器 E2E。不得无理由声称全量通过。
5. **真实路径证据**：只有在本次任务已授权的真实 URL、真实数据根、真实输入和真实浏览器动作均执行并可观察时，才报告相应范围的 `real-pass`。隔离测试、headless、静态扫描不得升级为真实用户路径通过。
6. 测试失败时，记录失败用例、断言、实际值和关联性。确认失败与本次差异无关后，标为“本次范围外未通过/待单独跟进”，不能隐藏失败，也不能把整体验证写成全通过。需要进一步修改无关模块才能继续时，先停止并确认范围。

### P4：交付与结论

按以下格式交付：

```text
任务：<编号 + 名称>
目标与范围：<简述>
状态：PASS / FAIL / BLOCKED / LIMITED / NOT_VERIFIED
修改文件：<逐项路径及改动>
验证：<命令/浏览器动作、结果、覆盖范围>
失败与未覆盖：<逐项列明；没有则写无>
边界：<说明结论只覆盖什么；不得推及整个产品>
后续：<被发现但未授权/未实施的问题>
```

对代码类 Buddy 任务，明确区分：

- `implemented`：实现已修改；
- `tested`：列出的测试实际通过；
- `scoped real-pass`：本次明确范围内真实用户路径有足够证据；
- `NOT_VERIFIED`：未实际覆盖的页面、数据根、浏览器路径、响应式维度或失败恢复。

完成任务后，只有用户明确要求时才提交、推送或清理其他文件。提交前单独核对暂存区，防止凭据、Cookie、数据库、真实资料、日志和测试产物进入版本库。

## 4. 文案任务专项检查表

适用于 P0-01 一类只改用户可见文案的任务：

- [ ] 先读取目标页与文案对应的设计标准、验收条款。
- [ ] 精确限定可见文字修改；不把文案任务扩大成结构、样式、状态或流程改造。
- [ ] 在目标页面和测试代码中搜索旧文案，识别断言、导航标题表和无 JS 路径。
- [ ] 只更新真实依赖旧可见文字的断言，不做无差别全仓替换。
- [ ] 保留 DOM 结构、链接、业务状态、测试选择器和辅助属性，除非任务明确要求改变。
- [ ] 运行所有直接相关的文案断言和至少一个目标页加载用例。
- [ ] 检查页面不再出现任务明确要求移除的旧文案；区分主标题、区域标题与仍允许存在的业务状态/loading 文案。
- [ ] 任何相关套件中的无关失败均如实报告，不归咎于本次改动，也不宣称整套 PASS。

## 5. 已验证的 P0-01 示例

2026-09-28 的 P0-01 实施遵循本流程：`today.html` 主标题改为“今天学什么？”，移除演示稿式眉标题和说明文字，区域标题改为“今天的学习”；同步更新 5 个直接依赖旧 H1 的浏览器 spec。

实际验证结果：文案直接聚焦用例 7/7 通过；扩展相关套件 25/26 通过，其中唯一失败为问答页等待文案断言收到“正在加载线程...”，与 P0-01 无关。`git diff --check` 和源码大小门禁通过。此证据仅覆盖该次改动和列出的用例，不代表后续任务或全站通过。

## 6. 目录与维护

- Buddy 功能实施流程放在 `docs/workflow/`。
- 本文是实施 workflow，不是 Buddy 产品需求、测试策略总表或 Agent 通用执行协议。
- 若流程与 `AGENTS.md`、AI Agent 执行模板或任务 Prompt 冲突，以上级文档和本次明确授权为准；发现冲突先暂停并澄清，不擅自覆盖规则。
- 每个任务的测试结果和实现状态应留在对应任务交付、既有状态文档或用户指定证据位置；不要把瞬时测试报告持续复制进本 workflow。
